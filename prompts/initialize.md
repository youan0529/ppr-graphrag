## Task
Given only the original question, identify named starting anchors and useful relation types for graph exploration. Do not answer the question or invent the names or values of unknown objects. Return one JSON object with exactly three fields: start_mentions, priority_relations, expanded_relations.

start_mentions: List entities directly named in the question that can be looked up by name. Distinguish an actual name from a description of an unknown object through a relationship. Follow nested descriptions back to their named anchors; do not use a bare role word or an unresolved relational phrase as an entity name. Preserve complete person names, work titles and organization names. Possessives, relationship words, and "of" inside a name do not automatically create extra participants. Starting names must occur in the question, case-insensitively. Dates and numbers alone are not starting entities.

priority_relations: List the directly useful relations and requested properties. Each hint connects two argument positions; it must not hide a third unnamed participant inside either endpoint. Split explicit nested relational descriptions into their component relations, including connecting relations and the final requested property. Judge meaning, not the number of occurrences of "of". A conventional compound relation word, such as grandmother, is itself a valid relation type and need not be decomposed to make this field valid. Preserve the original relation and meaningful qualifiers when expressed in the question. Do not replace a useful direct compound relation with only its underlying relations.

expanded_relations: Separately consider the relations already listed in priority_relations. For common compound relations whose decomposition is clear, add their useful basic relation types here. This is supplementary exploration information, not a replacement for priority_relations. Do not force a decomposition when it is uncertain, invent missing qualifiers, or copy example relations that do not apply. An empty list is valid. Do not merely repeat the compound relation or rewrite it as another nested endpoint description.

In BOTH relation fields, use generic subject/object placeholders X and Y instead of concrete names or unresolved role descriptions. Each hint independently describes one relation; placeholders are local to that hint, not bindings shared across a fixed traversal plan. Subject and object roles must be clear. Repeated use of the same relation type needs only one hint, and expanded_relations should not repeat a type already supplied in priority_relations. Keep all three fields as lists of strings. Return only JSON, without answers, explanations, triples, or a new execution-plan structure.

For a comparison, include the observable properties needed to decide it: comparing ages requires birth dates, and comparing establishment times requires founding dates. A comparison predicate alone does not retrieve these attributes. Preserve the bridges from each named object to the participant whose property is needed; do not guess property values.

## Example
Question: Where was the maternal grandfather of the director of the film "The Winter Orchard" born?
Output: {"start_mentions":["The Winter Orchard"],"priority_relations":["X was directed by Y","X has maternal grandfather Y","X was born in Y"],"expanded_relations":["X has mother Y","X has father Y"]}
